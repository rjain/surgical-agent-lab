The Lab, Block by Block

You build one system in three parts: a detector that uses no model, an explanation layer that does, and an agent over both. Then your group picks one of two things to build on top. This is what happens in each block and what you write.

The timings below are a suggested allocation, not a schedule. They are what the material is sized for; spend longer where it is interesting and we will tell you when to move on. The four building blocks fit in the first 100 minutes, leaving the last 30 for demos and closeout.
Start here. git pull, then streamlit run ui/app.py. If you set up last week and have not pulled since, you need to: we refresh the clip manifest on the morning of the session. If anything below fails, say so early rather than working around it.

Lab 1 about 15 min · nothing to write

Run the interface and read the Session tab. Pick a session marked · prepared; case_125 is the one to start on. You are looking at task steps, one lane per robot arm, and a mark wherever a rule fired.

Open a flagged moment. Each gives you two halves: what this rule looks for, and what it found here. Neither works alone, and the first is what makes the second worth reading. Below them are the instruments in play during the window. Then open lab/rules.py and find the rule that produced it.

Start with the Suturing overrun. It took 45.4 minutes against a corpus median of 8.0, and the same session does Suturing three other times in 1.4, 7.3 and 5.9 minutes. You do not need the corpus to see which one is odd, which is the clearest version of what these rules are for.

The point of this block, and of the whole day

Every flagged moment you are looking at was found by about two hundred lines of ordinary Python, in microseconds, with no model and no computer vision. Four rules over task and instrument logs: swap churn, step overrun against a corpus median, oscillation back to a step, and an unidentified instrument.

Nothing above this line needs a model, so nothing above this line gets one. Being able to make that argument, and to show where the line sits, is what you should leave with.

If you finish early, one of these rules is weaker than it looks. The thresholds at the top of lab/rules.py are tunable, and python -m lab.evaluate_rules --all reports what fires across all 155 sessions. A rule that never fires is dead weight; a rule that fires on the ordinary case teaches the room that the system cries wolf. One of the four is in the second category.

Counting flags will not settle it — two of the rules fire at almost the same rate. Ask instead whether a rule beats chance on the same data: python -m lab.evaluate_rules --distribution puts a null model behind each one. Find the weak rule, and decide what you would do about it. Raising its threshold is the obvious move and the wrong one; be ready to say why.

Lab 2 about 30 min · the dense block

A flag names a statistic. "Tool-swap churn at 137 seconds" is useless to the person who has to act on it. Your job is to turn one flagged window into a description they can act on, and then to refuse the descriptions you cannot defend.

You write two functions in lab/lab2_analyze.py:

analyze_clip(case_id, part, t_start, t_end) -> TechniqueNotes validate(notes, t_start, t_end) -> None, or raises GuardrailViolation

The schemas are given. TechniqueNotes and Observation are already defined, and getting the clip to the model is done for you: call lab.clips.resolve_clip().

  • Window it. Do not send the whole segment. A flagged segment is a whole task step, median eleven minutes. Every flag carries a watch_window: forty seconds around the instant that explains it. Roughly 10,000 tokens against 170,000, and the difference is what keeps twenty-five people inside one rate limit.
  • Give the model the flag. Do not ask the open question "what is wrong here". Tell it what the rules found and ask what is visible around that moment. The difference in output quality is not close.
  • Say what you are doing, so the interface can show it. Pressing Explain this moment opens a panel that lists each step as it happens. The supplied parts already report themselves: finding the clip, checking the pre-upload is still live, hitting the cache. The middle is yours, and goes quiet without a line from you. from lab import trace, then trace.step("sending 40s to gemini-flash-latest"). Worth it for your own sake: behind a spinner, a slow run and a broken run look identical.
  • Then write the guardrail, and prove it fires. The schema fixes the shape of a reply; it does nothing about a timestamp the model was never shown. validate() checks four things: every timestamp inside the window, not_visible non-empty, no clinical vocabulary, at least one observation. Do not wait for the model to misbehave. Hand validate() a TechniqueNotes you built by hand with a timestamp outside the window, and check it raises. Thirty seconds, deterministic, and it is how you would verify any check in real work. tests/test_guardrail.py does exactly this if you want the shape. Then, when the real thing fires, tighten the prompt and run again.

Done when the Explain this moment button on a flagged moment returns notes that survive your own validate().

The break choose your variant

The two variants are pitched just before the break. Decide as a group over it, so the fork starts with building rather than with a discussion.

Lab 3 about 20 min · short, and one exercise inside it

Three tools, one agent. The tools are thin wrappers around things that already work, including your own Lab 2. You write one function in lab/lab3_agent.py:

build_agent() -> google.adk.Agent # holding TOOLS, with an instruction

Give it an instruction whose first rule is that it must never state a number it did not get from a tool. That is checkable: the interface prints the tools an answer actually called, underneath the answer.

Do this before you tidy anything

One of the three tools ships with a deliberately useless docstring: """gets metrics""", with its arguments described as "the id" and "the step". Leave it alone at first. Run the agent on "where did I lose the most time in case_045?" and watch which tool it reaches for. Then write the docstring properly and run it again.

Measured over four runs each: the good docstring calls the right tool first every time, in three or four calls. The vague one picks wrong half the time, and on one run made eleven calls to answer the same question. Neither ever failed outright. A bad tool description does not break an agent, it makes it expensive and erratic, which is far harder to catch in review.

When the honest answer is "I cannot"

The console publishes 109 Objective Performance Indicators, and lab/opi.py carries all of them: the name the console uses, and its definition. Three can be computed from these labels: total duration, and how long each instrument was installed overall and per arm. The other 106 need forces, clutches, pedal presses and instrument path length, none of which SurgVU records.

So get_metrics answers a question about console movement % with that metric's real definition and the reason it cannot be computed, rather than with a number. That is the correct answer, not a bug. Getting your agent to report it plainly, instead of substituting something that looks close, is the harder half of the exercise.

One trap worth meeting on purpose. Our swaps_per_min counts instruments being exchanged. The console's arm_swap_freq is the rate of arm swaps, meaning the surgeon changing which arm the hand controllers drive. Same words, different event. The vocabulary belongs to the customer, and guessing at it produces confident nonsense.

Once it builds, look at it in Google’s own inspector
adk web adk_agents

Run that from the repository root and open the printed URL: your agent, in ADK’s dev UI, with an Events pane showing every tool call it makes and what came back — the raw trace behind the Coach tab. It refuses to load the agent until build_agent() exists, so if it loads, your Lab 3 is structurally right.

The fork about 30 min · build one

Both are built on the same three tools. Neither is more correct, and that is the point of running both in one room: the demo block puts them side by side.

Variant A · Debrief Coach

An agent you talk to. Someone asks about a session and gets an answer tied to a real measurement and a real timestamp, with the tool calls shown underneath. lab/variants/coach.py.

build_coach(tracker) build_workflow_tracker()

Minimum: one agent holding the three tools. Reach this first. Fuller: add a tracker that knows which flagged moments are still unreviewed.

The trap: wire the tracker as an AgentTool, not as a sub_agent. Transfer hands the conversation over, so your coach disappears mid-sentence and the trainee ends up talking to an agent with no conversational instruction. Most ADK material shows transfer first.

Variant B · Session Auditor

An agent you launch and leave. One action reviews a whole session and emits a typed report: ranked findings, evidence, recommendations, and what the review could not establish. lab/variants/auditor.py.

build_segment_analyst() build_synthesizer() build_auditor()

Minimum: a plain loop over the flagged windows, then one synthesis call. Fuller: fan out, with a bounded worker count.

Worth noticing: here the code decides what to fetch and the model only reasons over what it is handed. Predictable, and the right shape for anything unattended. Also: consider whether the "analyst" needs building at all, or whether Lab 2 already is one.

Reach the minimum form first. Both have one, so a group that runs late ships something smaller rather than nothing. Your variant's tab in the interface stays dark until the file is written, then comes alive.

Wrap the last 30 min · demos and closeout

One demo of each variant, the stretch briefs, and saving your work. Your checkout is already a git repository and the code runs from your own machine, so nothing you built depends on anything we switch off. Push it to your own remote if you want it somewhere else.

Two things that will save you time

  • Re-running a window is free. Clip analyses are cached to disk, so iterating on a prompt does not re-bill the same call. Delete .cache/ if you want a genuinely fresh one.
  • solutions/ holds a worked version of all four files. Reading one is a normal move, not a defeat. Write your own prompt first, because the prompt is where the learning is. To use one: cp solutions/lab2_analyze.py lab/lab2_analyze.py.
The framing, stated once

This reviews recorded training exercise footage. Deviations carry a score, never a severity or a risk. It is an educational exercise and not a medical device: no diagnosis, no patients, no clinical use. That is not a disclaimer bolted on afterwards. It is why Lab 2 has a guardrail and why the reports state what they could not establish.
